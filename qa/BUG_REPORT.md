# CampusPool Bug Report

Audit date: 2026-06-28. Open items are source-backed risks or product gaps;
database-dependent impact was not reproduced against a real test database.

| ID | Severity / priority | Title | Reproduction / expected vs actual | Root cause / impact | Affected files | Fix and regression verification |
|---|---|---|---|---|---|---|
| QA-01 | HIGH / P1 — fixed; superseded by Firebase auth | Legacy JWT authentication used a known built-in fallback | The original issue was token forgery when `JWT_SECRET` was omitted. | Custom JWT signing/verification was removed from the active authentication flow; protected endpoints now validate Firebase ID tokens, verified email claims, and the Firebase UID profile. | `backend/src/middleware/authMiddleware.js`, `backend/src/services/firebaseAdminService.js`, `backend/src/utils/firebaseIdentity.js`, `lib/services/auth_service.dart` | Removed custom token utility and dependency. Firebase identity and profile-provisioning regression tests pass. Firebase credentials and the database schema still need environment-specific deployment setup. |
| QA-02 | HIGH / P1 — fixed | Passenger boarding OTP included in driver/shared booking responses | Inspect driver responses from booking decision, request lists, ride details, and verification result. Expected: OTP only available to passenger; actual: full booking objects included it. | Prisma booking responses serialized every field by default, allowing a driver or other shared response recipient to obtain the passenger's code before checking it. | `backend/src/controllers/bookingController.js`, `backend/src/controllers/rideController.js`, `backend/src/utils/bookingPrivacy.js` | Shared responses now omit the OTP. Synthetic regression test passes. Passenger-owned booking responses retain the OTP. |
| QA-03 | HIGH / P1 — fixed | Ride lifecycle allowed invalid/reverse status changes | Request a scheduled→completed or cancelled→scheduled transition. Expected: reject; actual: any allowed enum value could overwrite current status. | Controller validated only the destination enum, not the current state; terminal rides could be reopened and scheduled rides completed without starting. | `backend/src/controllers/rideController.js`, `backend/src/utils/rideLifecycle.js` | Enforced scheduled→ongoing/cancelled and ongoing→completed only; updates are conditional on the previously read status. Transition regression test passes. Concurrency behavior still needs DB integration coverage. |
| QA-04 | MEDIUM / P2 — fixed | Reviews could be submitted before the ride completed | Submit a review for a ride with an accepted booking while ride is ongoing. Expected: reject; actual: accepted bookings were eligible. | Review logic accepted `ACCEPTED` bookings before completion despite the user journey indicating post-ride review. | `backend/src/controllers/reviewController.js`, `backend/test/authProfileRating.test.js` | Review creation now requires a completed ride and completed booking. Mocked controller regression test passes. |
| QA-05 | HIGH / P1 — partially fixed | General profile/ride responses exposed unnecessary student contact and identity data | Query profile/search/detail data as an authenticated user. Expected: minimum public fields; actual: profile/search/detail selected contact and student identifiers, and detail also exposed passenger identity fields. | Broad selectors returned personal fields without relationship-specific access checks. | `backend/src/controllers/userController.js`, `backend/src/controllers/rideController.js` | Removed email, phone, roll number, and plate from the general user profile; removed phone/roll number from ride search/detail; accepted passenger details in ride detail no longer include contact, roll number, or emergency phone. Remaining relationship-level access and all response surfaces need database/API isolation tests. |
| QA-06 | HIGH / P1 — open | Ride can be started without successful boarding OTP verification | From the driver ride controls, request `ONGOING` without calling OTP verification. Expected for a boarding safety gate: reject; actual: ride status endpoint accepts the transition without booking verification. | Ride lifecycle state is independent from OTP verification; OTP validation does not persist a verified state or gate the ride-start endpoint. | `backend/src/controllers/bookingController.js`, `backend/src/controllers/rideController.js`, `backend/prisma/schema.prisma`, `lib/screens/rides/my_rides_screen.dart` | Requires a product-approved lifecycle/data design (verification state, retry/expiry/reuse policy, and transaction semantics), likely a schema change. Not changed without approval. |
| QA-07 | HIGH / P1 — fixed; PostgreSQL integration verification blocked | Concurrent booking approvals may oversubscribe the last seats | With a ride having one seat and two pending one-seat requests, approve both concurrently. Expected: one succeeds, one conflicts, one seat is allocated. | Separate capacity read/check/write operations could let both approvals observe the same seat count. | `backend/src/controllers/bookingController.js`, `backend/src/services/bookingApprovalService.js`, `backend/test/bookingApproval.test.js` | Acceptance now uses an atomic conditional seat decrement (`availableSeats >= requestedSeats`, ride still `SCHEDULED`) and a conditional `PENDING`→`ACCEPTED` update in the same Prisma transaction. If either update affects zero rows, a 409 conflict is returned and the transaction rolls back. Concurrent in-memory regression test passes; PostgreSQL concurrency verification remains blocked because no isolated DB is available. |
| QA-08 | HIGH / P1 — implemented; end-to-end verification blocked | Student email verification was absent | Register a user without proving control of an official campus email. | The old custom signup flow did not verify campus email ownership before granting app access. | `lib/services/auth_service.dart`, auth screens, `backend/src/controllers/authController.js`, `backend/src/middleware/authMiddleware.js`, `backend/prisma/schema.prisma` | Signup now creates a Firebase email/password account and sends a verification link; login and backend profile provisioning require a verified exact `@vit.edu` identity. Existing records are not linked. Firebase configuration, schema application, and real email/device/API E2E testing are still required. |
| QA-09 | MEDIUM / P2 — open | OTP verification has no persisted one-time/attempt state | Submit a valid OTP repeatedly and inspect ride state. Expected safety behavior should define one-time use/limited attempts; actual controller only compares the stored value and responds success, with no consumed/attempt tracking. | Schema and handler do not persist verification outcome or limit repeated guesses; start is also not gated (QA-06). | `backend/src/controllers/bookingController.js`, `backend/prisma/schema.prisma` | Define policy and test with isolated DB; likely requires schema change. |
| QA-10 | MEDIUM / P2 — fixed | Backend could report healthy without a database URL | Start the API without `DATABASE_URL`. Expected: fail startup because core operations require PostgreSQL; actual: startup warned and continued to listen, while `/health` reported `ok`. | `connectToDatabase` treated missing database configuration as optional. | `backend/src/server.js`, `backend/src/utils/requiredEnvironment.js` | Startup now fails unless both `DATABASE_URL` and `FIREBASE_PROJECT_ID` are configured. `requiredEnvironment.test.js` passes. |

No database corruption, overbooking, or unauthorized access was claimed as
reproduced; those cases remain blocked for the reasons in `TEST_PLAN.md`.
